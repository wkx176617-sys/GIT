# 版本维护规则

## 两种版本号

- 工具版本：例如 `v1.2.0`，代表本仓库的脚本和教程版本。
- GOST 版本：例如 `3.2.6`，代表服务器中运行的代理核心版本。

两者不能混淆。GOST 升级必须先验证官方校验值、配置兼容性和代理连通性，再随新的工具版本发布。

## 分支与标签

- `main`：开发分支，保存下一版本的工作。
- `v主版本.次版本.修订版本`：不可移动的稳定标签，例如 `v1.2.0`。
- 实际部署只使用稳定标签，不直接部署 `main`。

版本号遵循语义化规则：

- 修订版本：错误修复，不改变用法，例如 `v1.2.1`。
- 次版本：兼容的新功能或新平台支持，例如 `v1.3.0`。
- 主版本：不兼容的配置、命令或迁移变化，例如 `v2.0.0`。

功能数量增加不是升级 `2.0` 的理由。只有无法保持兼容的安装、配置、命令、核心实现或产品
形态变化才使用新的主版本。详细准入标准见[项目宗旨与开发边界](project-principles.md)。

## 每次发布必须同步

1. 更新根目录 `VERSION`。
2. 更新 `README.md` 中的推荐版本。
3. 更新完整搭建教程中的下载命令和推荐版本。
4. 更新 macOS 和 Windows/Xshell 教程中的固定标签。
5. 在 `CHANGELOG.md` 添加版本摘要。
6. 新建 `docs/releases/vX.Y.Z.md` 详细说明。
7. 写明新增内容、修复内容、兼容性、升级步骤、回退步骤和已知限制。
8. 确认新手总路线和平台教程没有复制客户端、故障或插件专题。
9. 新手页面发生变化时同步导航清单并运行 `scripts/docs-navigation --write`。
10. 运行 `bash scripts/release-check.sh`。
11. 提交并推送 `main`。
12. 创建带说明的 Git 标签并推送。

每个新版本还必须说明复杂度与性能影响：是否新增常驻进程、端口、定时任务、依赖、用户步骤
或核心模块耦合。没有新增时也要明确写“无”。

任何一项缺失，都不应发布稳定标签。

## 历史不可改写

已推送的稳定标签不得删除、移动或覆盖。发现问题时发布新的修订版本，并在新旧版本说明中记录影响。密码、真实节点 IP、SSH 私钥和真实节点清单永远不能进入版本历史。
