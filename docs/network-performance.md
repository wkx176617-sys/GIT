本页只负责判断“代理能连接但很慢”的问题，以及管理主程序内置的 BBR + FQ。它不负责 IP、
DNS、WebRTC、时区或平台风控。

## 默认行为

从 `v1.12.0` 开始，首次安装和没有明确 BBR 记录的旧节点升级会自动质检并开启 BBR + FQ。
它不增加进程、端口或定时任务，只写入 `/etc/sysctl.d/99-gost-socks-bbr.conf`。旧插件已经开启
过 BBR 的节点会沿用相同状态文件和配置文件，无需先卸载。

查看状态：

```bash
socksctl bbr status
socksctl bbr health
```

明确关闭或重新开启：

```bash
socksctl bbr disable
socksctl bbr enable
```

关闭会恢复本项目首次接管前的拥塞算法和队列规则，并保存选择；后续升级不会擅自重新开启。
如需在首次安装或本次升级时直接关闭，可给安装命令或升级命令追加 `--no-bbr`。

## 先区分“隔离正确”和“线路够快”

公网 IP、DNS、WebRTC 和时区都正确，只能证明隔离一致，不能证明吞吐、抖动和丢包合格。
简单 IP 页面能打开、`socksctl check` 成功，也不能替代大文件和复杂网页测试。

遇到网页骨架长期不完成、视频打不开或 `ERR_SOCKS_CONNECTION_FAILED` 时，按顺序记录：

1. 下载、上传、空闲延迟、负载延迟、抖动和丢包；
2. 比特浏览器和另一个客户端是否同时异常；
3. 关闭或开启本地 VPN 后结果是否变化；
4. `socksctl doctor --no-record` 与 `socksctl bbr health` 的输出；
5. 同一供应商的其他 IP 是否也慢。

多个客户端同时变慢，通常更像共同线路、VPS 出口或节点问题；只有一个客户端异常，才优先检查
该客户端的代理模式、DNS、扩展和缓存。不同 IP 即使地理位置不同，也可能共享同一个 ASN、上游
或拥塞出口，批量购买前应先验收单节点。

## BBR 能做什么

BBR 主要改善 TCP 拥塞控制，常见收益是高延迟或有丢包线路上的下载吞吐和稳定性。它不能：

- 缩短物理距离决定的基础延迟；
- 修复低质量或被平台限制的 IP；
- 保证上传、所有网站或所有时段同幅度改善；
- 代替 DNS、WebRTC、IPv6 和时区验收；
- 把明文 SOCKS5 变成加密协议。

启用后要重新建立客户端连接再复测，并保留启用前后的同一测试条件。一次测速波动不足以证明
长期改善，至少比较多次结果和实际目标网站。

## 多跳与本地 VPN

可能存在这样的路径：

```text
比特窗口 → 本地 VPN 中转 → 最终 SOCKS5 节点 → 目标网站
```

只要最终检测到的公网 IP 仍是 SOCKS5 节点，这属于中转路径变化，不等于出口身份改变。服务器
日志里的客户端来源地址表示“谁连接了 SOCKS5”，不是目标网站看到的最终出口。多跳有时能改善
到 VPS 的路径，也会增加故障点；是否采用只能用同一窗口的出口 IP 和性能基线判断。

## 冲突与恢复边界

如果其他 `/etc/sysctl.conf` 或 `/etc/sysctl.d/*.conf` 也管理相同参数，主程序会停止，不争抢
设置。不要复制来历不明的“一键加速”脚本，不要关闭 TLS 校验，也不要安装定时反复覆盖 sysctl
的任务。

卸载主程序会先恢复本项目接管前的网络设置；恢复失败时卸载停止。未知配置冲突请先运行：

```bash
socksctl report
```

下一步只有一个：回到[客户端导入与网络验收](clients.md)，在同一客户端复测实际出口与速度。
